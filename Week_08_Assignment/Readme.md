# E-Commerce Order Analytics System

**Intern Mini Project — Week 8 | Skills: Python, SQL, Problem Solving**

An end-to-end pipeline that generates messy, realistic e-commerce data, cleans it,
loads it into a relational database, and answers business questions with SQL — from
basic aggregations to window functions and cohort analysis.

---

## 1. Problem Statement

Real-world order data is never clean. It comes from multiple systems, has missing
fields, inconsistent formats, and outright errors. This project simulates that
reality in miniature: four related tables (`customers`, `orders`, `order_items`,
`products`) are generated with **intentional data quality issues**, and the goal is
to build a pipeline that detects, documents, and fixes those issues before doing any
analysis on top of it.

The project is split into four stages that mirror a real data engineering workflow:

1. **Generate** — synthetic data with realistic dirt baked in
2. **Clean** — detect and fix (or flag) each issue
3. **Load & Analyze** — move clean data into SQLite, answer business questions in SQL
4. **Report** — a reusable command-line tool for on-demand summaries

`orders` and `order_items` are the transactional core, `customers` and `products`
are the reference/dimension tables around them.

## 3. Stage 1 — Data Generation

Each table is generated by its own script using the `Faker` library, and each one
injects a specific, realistic flaw so that Stage 2 has something real to clean:

| Table | Script | Intentional flaw injected |
|---|---|---|
| `customers.csv` | `cust_gen.py` | 10 rows get a malformed email (`invalidemail.com` — no `@`, no valid domain) |
| `orders.csv` | `order_gen.py` | 25 rows get a missing `customer_id`; 15 rows get their date written as `DD-MM-YYYY` instead of the standard `YYYY-MM-DD` |
| `order_items.csv` | `order_items_gen.py` | 15 rows get a negative `quantity`, representing a **return** rather than a purchase |
| `products.csv` | `product_gen.py` | 20 rows get a product name with extra padding and inconsistent case, e.g. `"  KEYBOARD  "` instead of `"Keyboard"` |

This mirrors how dirty data actually shows up in production: not randomly, but
along a handful of predictable failure patterns (bad user input, system defaults,
format mismatches between source systems, and legitimate business events like
returns being encoded oddly).

---

## 4. Stage 2 — Data Cleaning (`clean_data.ipynb`)

Cleaning is done table by table, and each fix is a deliberate decision rather than
a blanket "drop bad rows":

- **`orders.csv` — dates**: parsed with a mixed/day-first-aware date parser so both
  `YYYY-MM-DD` and `DD-MM-YYYY` rows resolve to the same correct datetime, instead of
  silently producing wrong dates or `NaT`.
- **`orders.csv` — missing `customer_id`**: rather than deleting these orders (which
  would understate total order volume), the missing value is filled with a
  placeholder (`0`) and cast to a nullable integer type, so the order stays visible
  in aggregate counts but is clearly identifiable as "customer unknown."
- **`products.csv` — product names**: whitespace is stripped and the string is
  converted to title case, so `"  KEYBOARD  "`, `"keyboard"`, and `"Keyboard"` all
  collapse into a single canonical value. This matters a lot for `GROUP BY`
  queries — without it, the same product would silently split into several "different"
  products in every aggregation.
- **`customers.csv` — emails**: since a broken email can't be repaired by guessing,
  it's validated with a regex (`something@something.something`) and flagged with a
  boolean column instead of being altered. The underlying business decision here is:
  *don't invent data, just make the problem visible.*
- **`order_items.csv` — referential integrity**: every `order_id` is checked against
  the actual set of order IDs in `orders.csv` to catch "orphan" line items that
  point to an order that doesn't exist — a common symptom of failed joins or partial
  writes upstream.

The output of this stage is a set of `clean_*.csv` files in `data/cleaned/`, which
are the only files the rest of the pipeline touches.

## 5. Stage 3 — Load & Analyze

### 5.1 Loading (`build_database.py`)
The four cleaned CSVs are loaded into a single SQLite file, `ecommerce.db`, with one
table per CSV. SQLite is used because it needs no server setup and the whole database
is just one portable file — good enough for analysis at this scale, and the SQL
itself would port to Postgres/MySQL with only minor syntax changes.

### 5.2 Analysis (`sql/all_queries.sql`)
16 queries, grouped by increasing complexity, each answering a specific business
question:

**Basic**
1. Total revenue per category
2. Top 10 customers by total order value
3. Month-wise order count for the last 12 months

**Intermediate**
4. Customers who ordered but never received a delivery
5. Products with more returns than purchases
6. Return rate per category

**Advanced (CTEs & Window Functions)**
7. Running total of revenue per region over time
8. `DENSE_RANK` of products by revenue within each category
9. Gap (in days) between a customer's consecutive orders, flagging "At Risk" customers whose average gap exceeds 30 days
10. Multi-level CTE segmenting customers into High/Medium/Low monthly spenders
11. `NTILE` quartile segmentation (Platinum/Gold/Silver/Bronze) by lifetime value
12. Year-over-year revenue comparison, month by month
13. First vs. most recent product category purchased per customer (detects taste/behavior shift)
14. Cumulative revenue contribution — what % of revenue comes from the top N% of customers
15. Cohort analysis — customers grouped by signup month, tracking retention into month 1/2/3
16. Products frequently bought together (self-join, deduplicated pairs)

The recurring revenue formula used throughout is:

```
revenue = quantity × unit_price × (1 − discount_percent / 100)
```

The `discount_percent / 100` conversion matters because the raw column stores a
whole number (e.g. `25` for 25%), not a fraction — a detail that's easy to get
wrong and silently produces revenue 100x too small.

## 6. Stage 4 — Reporting Tool (`CLI_report.py`)

A small interactive command-line tool that answers the recurring question *"how did
we do in period X compared to the period before it?"* without needing to re-run
raw SQL each time.

**What it does, conceptually:**
1. Asks for a report type (daily/weekly/monthly) and a date range
2. Pulls total orders, total revenue, and unique customers for that range
3. Pulls the top 3 products by revenue in that range
4. Automatically computes the *immediately preceding period of equal length* and
   shows percentage change in orders and revenue against it

This last step is the interesting design decision: instead of comparing to a fixed
period (like "same time last year"), it compares to whatever period of the same
duration came right before — so a 9-day range is compared to the 9 days before it,
making the comparison fair regardless of what range the user picks.

**Run it with:**
```bash
python scripts/CLI_report.py
```

## 7. How to Reproduce End-to-End

```bash
# Stage 1 — generate raw data (writes into data/raw/)
python scripts/cust_gen.py
python scripts/order_gen.py
python scripts/order_items_gen.py
python scripts/product_gen.py

# Stage 2 — clean the data (run clean_data.ipynb top to bottom)
#   -> outputs clean_*.csv into data/cleaned/

# Stage 3 — load cleaned data into SQLite
python scripts/build_database.py

# Stage 3 (analysis) — run the queries
sqlite3 ecommerce.db < sql/all_queries.sql

# Stage 4 — generate an on-demand report
python scripts/CLI_report.py
```
